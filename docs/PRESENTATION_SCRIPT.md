## 1. 팀원 설명용 (약 3분)

> 서비스 아키텍처 그림을 띄워 놓고 ①부터 ⑤까지 손으로 짚으며 설명합니다.

RoadPush 백엔드가 하는 일은 한 문장으로 **"사진 한 장을 받아서, 걸을 통로가 남아 있는지 판정하고, 그 뒤의 사람 처리까지 기록하는 것"** 입니다.

**① 등록.** 현장 촬영자가 `/report` 화면에서 사진을 고르면, 백엔드가 먼저 사진 안의 촬영 시각과 GPS를 읽어 줍니다. 그 위치 근처에 이미 등록된 구간이 있으면 후보로 보여 주고, 사용자가 "이 구간이 맞다"고 고르거나 새 구간을 만듭니다. 가깝다는 이유만으로 자동으로 묶지 않는 게 중요합니다. 등록 버튼을 누르면 백엔드는 원본을 저장하고 **분석을 기다리지 않고 바로 "접수됨(202)"으로 답합니다.**

**② 대기열.** 분석은 오래 걸릴 수 있어서 따로 돌립니다. 등록할 때 분석 작업 한 줄이 `pending`으로 쌓이고, 분석 워커가 하나씩 꺼내 처리합니다. 실행 중 오류가 나면 최대 3번까지 다시 시도하고, 사진이 깨져 있으면 재시도 없이 실패로 끝냅니다.

**③ AI 분석.** 워커가 AI 팀의 RoadPush_AI를 함수로 한 번 부릅니다. 안에서는 두 갈래가 돕니다.
- 보행 통로: Mask2Former로 보도와 차도를 나누고 → 걸을 면을 고르고(Phase 6) → 양쪽 경계를 잡고(7-A) → 끊기지 않는 통로의 가장 좁은 비율을 잽니다(7-B).
- 막은 원인: YOLO11s로 차량·공사시설·적치물·PM을 찾고, 그중 **실제로 통로를 막은 것만** 원인으로 붙입니다.

백엔드는 AI가 낸 값을 다시 계산하지 않고 정해진 규칙으로 판정만 합니다. 결과는 통과 가능, 좁아짐, 단절, 판단 유보 넷 중 하나입니다. **측정할 수 없으면 0%나 통과로 채우지 않고 "판단 유보 + 사유"로 남깁니다.**

**④ 저장.** 판정, 상대 위험도, 원인, 근거 이미지, 그리고 어떤 모델·규칙 버전으로 나온 결과인지까지 Supabase DB와 파일 저장소에 기록합니다. AI 원본 응답도 통째로 남겨서 나중에 다시 확인할 수 있습니다.

**⑤ 확인·조치.** 관리자는 `/dashboard`에서 지도와 목록으로 결과를 봅니다. AI 판정을 확인하거나 고치고(오탐 사유 포함), 처리 상태와 담당 부서를 정하고, 메모를 남깁니다. 이때 **AI 결과는 그대로 두고 사람 판정을 따로 저장**합니다. 조치 후 같은 구간을 다시 찍으면 ①부터 다시 돌고, 조치 전후를 같은 기준으로 비교합니다.

**정리하면**, 프론트는 백엔드 주소 하나만 알고, AI는 백엔드 서버 안에서 함수로 불립니다. 그래서 화면이 바뀌어도 AI는 그대로이고, 모델이 바뀌어도 화면은 그대로입니다. 배포 서버가 바뀌어도 프론트에는 백엔드 주소만 다시 넣으면 됩니다.

## 2. 발표 대본 (발표 자료 13쪽, 약 7분)

| 쪽 | 시간 | 화면 | 말할 내용 |
|---|---|---|---|
| 1 | 0:20 | 표지 | 안녕하세요, RoadPush 백엔드를 맡은 [이름]입니다. 사진 한 장에서 현장 조치까지, 백엔드가 서비스를 어떻게 잇는지 말씀드리겠습니다. |
| 2 | 1:00 | 서비스 아키텍처 | 전체 구성입니다. 사용자는 현장 촬영자와 지자체 관리자입니다. 둘 다 Vercel에 올린 웹 화면을 쓰고, 화면은 백엔드의 REST API만 부릅니다. 가운데가 백엔드 서버이고, 그 중심에 **AI 분석 엔진**이 있습니다. 결과는 Supabase PostgreSQL과 파일 저장소에 기록합니다. 번호 ①부터 ⑤가 사진 한 장이 지나가는 순서입니다. |
| 3 | 0:30 | 저장소별 역할 | 저장소는 프론트, 백엔드, AI 셋입니다. 프론트와 AI는 서로 직접 통신하지 않고, 모든 판정과 사람의 기록은 백엔드를 거쳐 DB에 남습니다. |
| 4 | 0:50 | 서비스 흐름 ①~⑤ | 등록하면 바로 접수하고, 분석은 대기열에서 따로 돕니다. AI가 통로 폭과 원인을 계산하면 근거와 모델 버전까지 저장하고, 관리자가 확인하고 조치합니다. 측정이 불가능하면 억지로 판정하지 않고 판단 유보로 사람에게 넘깁니다. 조치 후 다시 찍으면 같은 흐름으로 전후를 비교합니다. |
| 5 | 0:25 | 백엔드 계층 | 백엔드는 API, 서비스, AI 엔진, 데이터 네 계층입니다. AI 엔진은 DB를 모르는 분석 모듈이라 모델을 바꿔도 위 계층은 그대로입니다. |
| 6 | 0:35 | 분석 대기열 | 분석 작업은 대기, 분석 중, 완료, 실패 네 상태로 관리합니다. 실행 오류는 최대 3번 다시 시도하고, 손상된 사진은 바로 실패입니다. 서버가 꺼졌다 켜지면 처리 중이던 작업을 다시 대기로 돌립니다. 판단 유보는 실패가 아니라 완료이고, 검수 대상이 됩니다. |
| 7 | 0:45 | AI 연동 | AI 팀의 통합 진입점을 사진 한 장당 한 번 부릅니다. 보도와 차도를 나누고, 걸을 면을 고르고, 경계를 잡고, 끊기지 않는 통로의 가장 좁은 비율을 잽니다. 원인은 통로를 실제로 막은 물체만 씁니다. 백엔드는 이 값을 다시 계산하지 않고, AI 원본 응답과 모델 버전을 그대로 저장합니다. |
| 8 | 0:35 | 판정 규칙 | 걸을 면을 못 정했거나 경계를 사람이 봐야 하거나 통로를 잴 수 없으면 판단 유보입니다. AI가 확정한 경우에만 판정과 상대 위험도를 냅니다. 남은 통로 60% 이상은 통과, 30% 미만은 단절이고, 이 기준은 현장 실측으로 보정할 대상이라 버전과 함께 기록합니다. |
| 9 | 0:25 | API 계약 | 지도, 목록, 상세 화면은 모두 같은 응답 형식 하나로 그립니다. 처리 상태, AI 판정, 사람 검수가 서로 다른 필드라서, AI는 좁아짐인데 사람이 통과로 고쳤다는 사실이 둘 다 남습니다. |
| 10 | 0:25 | 데이터 모델 | 모든 기록의 기준은 구간입니다. 구간에 관측이 쌓이고, 관측마다 분석이, 분석마다 사람 검수가 붙습니다. 현장 조치는 조치 전 관측과 조치 후 관측을 이어 전후 비교의 근거가 됩니다. |
| 11 | 0:25 | 배포 구성 | 화면은 Vercel, API와 분석은 HTTPS가 붙은 백엔드 서버 한 대, 기록은 Supabase입니다. 키와 DB 비밀번호는 서버 환경 변수에만 둡니다. 서버 종류는 바뀔 수 있고, 바뀌어도 프론트에는 주소만 다시 연결하면 됩니다. |
| 12 | 0:25 | 신뢰성 | 지자체가 근거로 쓰려면 기록을 믿을 수 있어야 합니다. 실패와 재시도를 구분하고, AI와 사람 판정을 따로 남기고, 버전을 기록하고, DB 외부 접근을 막고, 자동 테스트 59개로 변경마다 확인합니다. |
| 13 | 0:35 | 한계와 다음 단계 | 한계도 말씀드리겠습니다. CPU 서버라 분석이 느리고, 로그인이 없는 시연용이며, 얼굴·번호판 비식별 방법은 [확정 중 / 적용 방식]입니다. 입력은 지금 사진 업로드이고 CCTV·단속 차량·드론 연동은 확장 과제입니다. 등록, 분석, 판정, 조치를 분리해 두었기 때문에 이런 확장은 해당 부분만 바꾸면 됩니다. 감사합니다. |

**말할 때 지킬 것**
- "불법 주정차", "방치"라고 단정하지 않습니다 → "보도 위 차량", "원인 후보"
- 위험도는 "상대 위험도"라고 부르고, 사고 감소를 주장하지 않습니다
- 수치는 자료에 있는 것만 말합니다 (재시도 3회, 기준 60%·30%, 테스트 59개)

## 3. 데모 영상용 백엔드 설명 (약 40초)

> 화면 녹화에 맞춰 읽습니다. ( ) 안은 화면 동작입니다.

(현장 촬영 화면에서 사진 선택) 사진을 고르면 촬영 시각과 위치를 읽고, 근처 구간을 보여 줍니다.
(등록) 등록은 바로 접수되고, 분석은 대기열에서 따로 진행됩니다.
(대시보드에서 "AI 분석 대기 중"이 결과로 바뀜) AI가 남은 통로 폭과 막은 원인을 계산해 판정합니다.
(상세에서 근거 이미지) 판정의 근거 이미지와 원인이 함께 저장됩니다.
(판정 수정 · 처리 상태 변경) 관리자는 AI 판정을 확인하거나 고치고, 담당 부서와 처리 상태를 정합니다. AI 결과는 지우지 않고 사람 판정을 따로 기록합니다.
(판단 유보 목록) 사진만으로 확정할 수 없는 건은 판단 유보로 모아 사람이 봅니다.

## 4. 예상 질문과 답

| 질문 | 답 |
|---|---|
| 사진 한 장으로 폭을 어떻게 아나요? | 사진만으로는 축척을 몰라 미터는 알 수 없습니다. 그래서 같은 단면의 전체 보행폭 대비 남은 통로 **비율**로 판정합니다. 구간에 실측 보도 폭이나 공공데이터 보도 폭이 있으면 미터 추정값을 참고로 덧붙입니다. |
| AI가 틀리면요? | 확정하지 못하는 건은 판단 유보로 사람에게 넘기고, 관리자가 판정을 고칠 수 있습니다. AI 원본 결과와 사람 판정, 오탐 사유가 모두 남아 다음 보정의 근거가 됩니다. |
| 왜 바로 결과를 주지 않고 대기열을 쓰나요? | 분석에 시간이 걸리고 서버의 계산 자원이 하나라서, 등록은 바로 접수하고 분석은 순서대로 처리합니다. 화면이 멈추지 않고, 오류가 나도 자동으로 다시 시도합니다. |
| 차량이 있으면 불법 주정차로 처리하나요? | 아닙니다. 원인은 "보도 위 차량"처럼 물체 이름만 붙이고, 단속 여부는 담당 부서가 판단합니다. 백엔드는 처리 경로와 기록만 돕습니다. |
| 모델이 바뀌면 이전 결과는요? | 분석마다 모델·규칙 버전을 저장합니다. 전후 비교는 버전이 같을 때만 지표를 비교하고, 다르면 같은 기준으로 재분석하도록 안내합니다. 이전 결과는 지우지 않습니다. |
| 개인정보는 어떻게 하나요? | 직접 촬영 사진의 얼굴·번호판은 비식별이 필요합니다. [적용 방식 또는 "저장 전 비식별을 적용할 예정"]. DB는 외부 접근을 막고 키는 서버에만 둡니다. |
| 다른 지역으로 넓힐 수 있나요? | 구간과 도로 링크 기준으로 기록하므로 지역 데이터만 추가하면 됩니다. 전국 규모가 되면 DB에 공간 인덱스(PostGIS)를 붙입니다. |
| 배포가 바뀌면요? | 백엔드는 서버 한 대에 HTTPS만 붙이면 되는 구조입니다. 서버가 바뀌어도 프론트에는 주소만 다시 넣으면 됩니다. |
