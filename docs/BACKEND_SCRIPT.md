## 1쪽 · 표지 (20초)

**말할 내용**
안녕하세요, RoadPush 백엔드를 맡은 [이름]입니다. RoadPush는 보도 사진 한 장으로 보행자가 차도로 내려가지 않고 걸을 통로가 남아 있는지 판정하는 서비스입니다. 저는 사진이 들어와서 판정이 나오고, 사람이 검수하고 조치하는 데까지, 그 사이를 잇는 백엔드를 말씀드리겠습니다.

## 2쪽 · 서비스 아키텍처 (80초)

**짚을 곳** 왼쪽 사용자 → 프론트 → 가운데 백엔드 서버 → AI 분석 엔진 → 오른쪽 DB·파일 저장소, 번호 ①~⑤

**말할 내용**
전체 구성입니다. 왼쪽부터 보시면, 사용자는 현장 촬영자와 지자체 관리자 두 종류입니다. 둘 다 Vercel에 올린 웹 화면을 쓰는데, 현장 촬영자는 사진 등록 화면, 관리자는 대시보드를 씁니다.

화면은 백엔드의 REST API 하나만 부릅니다. 가운데 큰 상자가 백엔드 서버입니다. 맨 위에서 HTTPS 요청을 받아 FastAPI가 처리하고, 분석 작업은 대기열에 넣어 워커가 꺼내 갑니다.

그 아래 가장 큰 상자가 **AI 분석 엔진**입니다. AI 팀의 RoadPush_AI를 백엔드 서버 안에 설치해 함수로 부릅니다. 네트워크를 한 번 더 타지 않아서 사진을 주고받는 비용이 없고, 모델은 서버가 켜질 때 한 번만 올립니다.

결과는 오른쪽 Supabase PostgreSQL과 파일 저장소에 기록합니다. 번호 ①부터 ⑤가 사진 한 장이 지나가는 순서이고, 바로 다음 장에서 자세히 보겠습니다.

배포 환경은 바뀔 수 있어 서버를 한 덩어리로 그렸습니다. 서버가 바뀌어도 화면에는 백엔드 주소만 다시 넣으면 됩니다.

## 3쪽 · 저장소별 역할 (30초)

**짚을 곳** 표의 "백엔드와 연결" 열

**말할 내용**
저장소는 프론트, 백엔드, AI 셋입니다. 연결 방식을 보시면 프론트는 REST, AI는 함수 호출, DB는 SQL입니다. 중요한 점은 **프론트와 AI가 서로 모른다**는 것입니다. 모든 판정과 사람의 기록은 백엔드를 거쳐 DB에 남습니다. 그래서 AI 팀은 화면을 신경 쓰지 않고 모델을 고치고, 프론트 팀은 모델을 몰라도 화면을 만들 수 있었습니다.

## 4쪽 · 서비스 흐름 ①~⑤ (70초)

**짚을 곳** 카드 다섯 개를 왼쪽부터, 아래 두 상자

**말할 내용**
① **등록**입니다. 사진을 올리면 백엔드는 먼저 사진의 EXIF에서 촬영 시각과 GPS를 읽고, 반경 50m 안의 기존 구간을 후보로 줍니다. 가깝다는 이유만으로 같은 구간으로 묶지 않고 사람이 고릅니다. 등록하면 원본을 저장하고 바로 **202 Accepted**로 답합니다.
② **대기열**입니다. 등록과 동시에 분석 작업 한 줄이 pending 상태로 쌓입니다.
③ **AI 분석**입니다. 워커가 작업을 꺼내 AI 엔진을 부르고, 남은 통로 폭과 막은 원인을 받습니다.
④ **저장**입니다. 판정, 상대 위험도, 원인, 근거 이미지, 그리고 어떤 모델과 규칙으로 나온 결과인지 버전까지 저장합니다.
⑤ **확인·조치**입니다. 관리자가 대시보드에서 보고 검수하고, 처리 상태와 메모를 남깁니다.

아래 왼쪽을 보시면, ③에서 통로를 확정하지 못하면 사유와 함께 **판단 유보**로 저장하고 ⑤에서 사람이 판정합니다. 오른쪽은 조치 후 같은 구간을 다시 찍으면 ①부터 다시 돌아, 조치 전후를 같은 기준으로 비교한다는 뜻입니다.

## 5쪽 · 백엔드 내부 계층 (50초)

**짚을 곳** 위에서 아래로 네 줄, 특히 AI 엔진 줄

**말할 내용**
백엔드 코드는 네 계층입니다. 위에서부터 요청이 내려가고, 아래 계층은 위 계층을 모릅니다.

**API 계층**은 요청을 받고 응답 형식을 맞춥니다. 응답 형식은 마스터 문서 4.4의 공통 분석 응답을 그대로 따릅니다.
**서비스 계층**은 대기열 처리, AI 호출과 결과 저장, 응답 조립, 촬영 위치와 주소 처리, 참조 데이터 조회를 맡습니다.
**AI 엔진 계층**이 핵심입니다. 이 계층은 **DB를 전혀 모릅니다.** 사진을 받아 결과만 돌려줍니다. 그래서 모델을 바꾸거나 AI 팀이 새 버전을 내도 위 계층은 그대로입니다. 모델 없이도 화면 연결을 시험할 수 있도록 가짜 엔진(dummy)도 같은 자리에 꽂을 수 있습니다.
**데이터 계층**은 SQLAlchemy와 Alembic입니다. 테이블은 7개이고, 스키마는 마이그레이션으로만 바꿉니다.

## 6쪽 · 분석 대기열 (80초)

**짚을 곳** 왼쪽 상태 흐름도 → 점선 재시도 화살표 → 오른쪽 카드 세 개

**말할 내용**
분석에 대기열을 쓴 이유는 세 가지입니다.

첫째, 분석에 시간이 걸립니다. 서버 사양에 따라 사진 한 장에 몇 초에서 그 이상 걸리는데, 그동안 화면이 기다리면 안 됩니다. 그래서 등록은 **202로 바로 답하고**, 화면은 "분석 대기 중"을 보여 주다가 결과가 나오면 바뀝니다.

둘째, 모델은 메모리를 많이 씁니다. 그래서 **워커 하나가 모델을 한 번만 올리고** 순서대로 처리합니다. 요청마다 모델을 새로 올리지 않습니다.

셋째, 실패를 구분하기 위해서입니다. 상태는 대기, 분석 중, 완료, 실패 네 가지입니다. 사진이 깨진 것 같은 **입력 오류**는 다시 해도 똑같이 실패하므로 바로 실패로 끝냅니다. 반면 실행 중에 난 오류는 같은 작업을 **첫 시도 포함 최대 3회**까지 자동으로 다시 시도합니다.

대기열은 별도 메시지 큐 없이 **analyses 테이블 자체**를 씁니다. 워커는 대기 중인 행 하나를 "분석 중"으로 바꾸면서 가져가는데, 이때 "아직 대기 중일 때만 바꾼다"는 조건을 걸어 두 워커가 같은 작업을 가져가지 않게 합니다. 서버가 분석 도중에 꺼지면, 다시 켤 때 "분석 중"으로 남은 작업을 대기로 되돌려 이어서 처리합니다.

마지막 카드가 중요합니다. **판단 유보는 실패가 아닙니다.** 분석은 정상적으로 끝났고, AI가 확정할 수 없다고 정직하게 답한 것입니다. 그래서 완료로 저장하고 사람 검수로 넘깁니다.

## 7쪽 · AI 연동 (80초)

**짚을 곳** 위 주황 상자의 두 줄(보행 통로 · 원인) → 아래 화살표 → 어두운 카드 세 개

**말할 내용**
AI 팀의 통합 진입점을 사진 한 장당 **한 번** 부릅니다. 안에서는 두 갈래가 돕니다.

위 줄은 보행 통로입니다. Mask2Former로 보도와 차도를 나누고, Phase 6에서 걸을 면을 고르고, 7-A에서 양쪽 경계를 직선으로 잡고, 7-B에서 위아래로 끊기지 않고 이어지는 통로 중 가장 좁은 곳의 비율을 잽니다.
아래 줄은 원인입니다. YOLO11s가 차량, 공사시설, 적치물, PM을 찾고, 그중 **7-B에서 실제로 통로를 막은 영역과 겹친 것만** 원인으로 붙입니다.

백엔드가 이 결과를 받아 하는 일은 아래 세 카드입니다.
첫째, phase7.py가 **값을 다시 계산하지 않고** 정해진 소비 규칙으로 판정만 합니다. AI 팀과 "이 필드가 비어 있으면 0으로 바꾸지 않는다" 같은 계약을 맞췄습니다.
둘째, causes.py가 원인을 배지와 처리 유형 A부터 D로 바꿉니다. 이 유형이 화면에서 담당 부서와 처리 안내로 이어집니다.
셋째, AI 원본 응답 전체와 모델 버전을 evidence에 **그대로 저장**합니다. 나중에 "왜 이렇게 판정했나"를 다시 확인할 수 있습니다.

## 8쪽 · 판정 규칙 (60초)

**짚을 곳** 표 다섯 줄 → 아래 두 카드

**말할 내용**
AI 결과를 판정으로 바꾸는 규칙입니다. 위 세 줄은 모두 **판단 유보**입니다. 걸을 면을 못 정했거나, 경계를 사람이 봐야 하거나, 통로 비율을 잴 수 없는 경우입니다. 이때 위험도는 계산하지 않고 비워 둡니다.

아래 두 줄이 자동 판정입니다. AI가 확정해서 판정을 냈으면 그대로 쓰고, 실제 폭 정보 없이 상대폭만 있으면 남은 통로 비율 60% 이상은 통과, 30% 미만은 단절, 그 사이는 좁아짐으로 봅니다.

왼쪽 아래 카드가 이 서비스의 원칙입니다. **모르는 것은 모른다고 답한다.** 측정하지 못한 값을 0%나 통과로 채우는 순간, 지자체는 잘못된 근거로 움직이게 됩니다. 오른쪽 카드처럼 60%와 30%는 현장 실측으로 보정할 값이라, 판정마다 규칙 버전을 함께 저장합니다.

## 9쪽 · API 계약 (50초)

**짚을 곳** 왼쪽 엔드포인트 표 → 오른쪽 응답 예시의 processing_status · passability · review_status

**말할 내용**
주요 엔드포인트는 등록, 조회, 검수, 재분석, 조치, 비교로 나뉩니다. 오른쪽은 응답 예시입니다.

여기서 세 필드를 봐 주십시오. processing_status는 분석이 끝났는지, passability는 AI가 뭐라고 판정했는지, review_status는 사람이 확인했는지입니다. 이 셋을 **한 필드로 합치지 않았습니다.** 예를 들어 AI는 좁아짐, 사람은 통과로 고친 경우에 둘 다 남아야 나중에 AI 오탐을 모아 개선할 수 있기 때문입니다.

지도, 목록, 상세, 판단 유보 화면이 모두 이 응답 형식 하나로 그려집니다. 전체 명세는 서버의 /docs 화면에서 바로 호출해 볼 수 있습니다.

## 10쪽 · 데이터 모델 (50초)

**짚을 곳** 가운데 줄 sites → observations → analyses → reviews, 아래 actions의 점선 "전후"

**말할 내용**
모든 기록의 기준은 **구간**입니다. 한 구간에 여러 번 찍은 관측이 쌓이고, 관측 하나에 분석이 여러 번 있을 수 있고, 사람 검수는 특정 분석에 붙습니다.

그래서 재분석을 하면 새 분석 행이 생기고, 이전 분석과 그 검수는 지워지지 않습니다. 새 분석은 미검수부터 다시 시작합니다.

현장 조치는 "조치 전 관측"과 "조치 후 관측"을 이어 줍니다. 점선이 그 연결입니다. 이게 전후 비교의 근거가 됩니다. 메모는 처리 상태와 따로 저장하고, 오른쪽 참조 레이어는 팀원이 공공데이터로 만든 도로 링크와 보도 폭 정보입니다. 구간을 등록할 때 가까운 링크를 찾아 붙입니다.

## 11쪽 · 배포 구성 (40초)

**짚을 곳** 표 → 아래 배포 순서

**말할 내용**
화면은 Vercel 서울 리전, API와 분석은 HTTPS가 붙은 백엔드 서버 한 대, 기록은 Supabase입니다. 키와 DB 비밀번호는 Vercel과 서버의 환경 변수에만 두고 저장소에는 넣지 않습니다.

배포 순서는 아래와 같습니다. 모델 없이 가짜 엔진으로 먼저 띄워 HTTPS와 화면 연결을 확인하고, 그다음 모델을 올리고 시연 데이터를 넣습니다. 이렇게 단계를 나눈 이유는 문제가 생겼을 때 네트워크 문제인지 모델 문제인지 바로 구분하기 위해서입니다.

## 12쪽 · 신뢰성 (50초)

**짚을 곳** 카드 여섯 개를 위 줄 → 아래 줄

**말할 내용**
지자체가 이 기록을 근거로 움직이려면 기록을 믿을 수 있어야 합니다. 그래서 여섯 가지를 넣었습니다.
실패와 재시도를 구분하고, AI 결과와 사람 판정을 따로 남기고, 모델·규칙 버전을 기록해 버전이 같을 때만 전후 수치를 비교합니다.
Supabase는 모든 테이블에 RLS를 켜서 외부에서 DB에 직접 접근하지 못하게 막았고, API 키는 서버에만 둡니다.
스키마는 마이그레이션으로만 바꾸고 서버가 켜질 때 자동으로 적용됩니다. 마지막으로 자동 테스트 59개가 API, 판정 규칙, AI 연결, 배포 설정을 바꿀 때마다 확인합니다.

## 13쪽 · 한계와 다음 단계 (50초)

**짚을 곳** 표 여섯 줄 → 마지막 문장

**말할 내용**
한계도 말씀드리겠습니다. CPU 서버라 분석이 느려서 시연 데이터는 미리 분석해 둡니다. 사진은 지금 서버 디스크에 있어 서버를 지우면 함께 사라지는데, 다음 단계에서는 객체 저장소로 옮깁니다. 지금은 로그인이 없는 시연용이고, 실제 운영에서는 담당자 계정과 부서별 권한이 필요합니다. 공간 조회는 성남과 서울 범위라 코드로 충분하지만 전국이 되면 PostGIS 공간 인덱스를 씁니다. 입력은 사진 업로드이고 CCTV·단속 차량·드론은 확장 과제이며, 얼굴·번호판 비식별 방법은 [확정 중 / 적용 방식]입니다.

마지막 문장이 이 구조의 핵심입니다. **등록, 분석, 판정, 조치를 서로 분리해 두었기 때문에**, 입력 수단이나 지역이 늘어나도 해당 부분만 바꾸면 됩니다. 감사합니다.

## 백엔드 기술 질의응답

### 설계

| 질문 | 답 |
|---|---|
| 왜 FastAPI인가요? | AI 모델이 Python이라 같은 프로세스에서 바로 부를 수 있고, 요청·응답 형식을 Pydantic으로 선언하면 검증과 API 문서(/docs)가 자동으로 나옵니다. |
| 왜 Redis·Celery 같은 메시지 큐를 안 썼나요? | 워커가 하나이고 작업량이 많지 않아, 분석 기록 테이블 자체를 대기열로 쓰는 것이 가장 단순했습니다. 작업 상태와 결과가 한 곳에 있어 "지금 몇 건이 대기 중인지"를 SQL 한 줄로 봅니다. 처리량이 커지면 큐를 붙여도 서비스 계층만 바뀝니다. |
| 워커 두 개가 같은 작업을 가져가면요? | 가져갈 때 "상태가 아직 pending인 행만 processing으로 바꾼다"는 조건부 갱신을 써서, 한쪽만 성공합니다. |
| 서버가 분석 도중 꺼지면요? | 다시 켤 때 processing으로 남은 작업을 pending으로 되돌려 이어서 처리합니다. 사진과 작업 기록은 DB와 저장소에 이미 있어 잃어버리지 않습니다. |
| 왜 결과를 바로 안 주고 202인가요? | 분석에 시간이 걸려 요청을 붙잡고 있으면 연결이 끊기거나 화면이 멈춥니다. 접수만 하고 바로 답한 뒤, 화면이 주기적으로 다시 조회해 결과로 바꿉니다. |
| 실시간 알림(WebSocket) 대신 다시 조회하는 이유는요? | 관리자 화면 특성상 몇 초 늦어도 문제가 없고, 주기적 조회가 배포·프록시 환경에서 가장 덜 깨집니다. |
| AI 엔진을 별도 서버로 안 뺀 이유는요? | 지금 규모에서는 같은 서버 안에서 함수로 부르는 게 사진 전송 비용과 장애 지점이 적습니다. AI 엔진 계층이 DB를 모르게 만들어 두어서, 나중에 별도 서버로 떼어도 서비스 계층의 호출부만 바꾸면 됩니다. |

### 데이터 · 정합성

| 질문 | 답 |
|---|---|
| 재분석하면 이전 결과는요? | 지우지 않습니다. 새 분석 행이 생기고, 이전 분석과 검수는 이력으로 남습니다. 시작 전인 재분석 요청은 취소할 수 있고, 취소하면 이전 결과로 돌아갑니다. |
| 사람이 판정을 고치면 AI 결과가 바뀌나요? | 아니요. 사람 판정은 검수 테이블에 따로 저장하고, 지도 색만 "사람 판정 우선"으로 보여 줍니다. |
| 시간대는 어떻게 처리하나요? | 등록할 때 시간대가 없는 시각은 거부하고, DB에는 UTC로 저장해 응답에서 한국 시간(+09:00)으로 바꿔 줍니다. |
| 구간은 왜 사람이 정하나요? | GPS는 촬영자 위치라 장애물 위치와 다를 수 있습니다. 거리만으로 자동으로 묶으면 다른 구간의 기록이 섞이므로, 후보만 주고 사람이 확정합니다. |
| 스키마는 어떻게 바꾸나요? | Alembic 마이그레이션으로만 바꾸고 서버가 켜질 때 자동 적용됩니다. 지금 0001~0003까지 있습니다. 대시보드에서 직접 열을 바꾸지 않습니다. |
| 로컬과 배포 DB가 다르면요? | 같은 SQLAlchemy 코드로 SQLite와 PostgreSQL을 모두 다루고, 같은 테스트를 PostgreSQL로도 돌릴 수 있습니다. |

### 보안 · 운영

| 질문 | 답 |
|---|---|
| 인증이 없는데 괜찮나요? | 시연용이라 로그인이 없고, 그 점을 한계로 밝힙니다. 대신 DB는 RLS로 외부 직접 접근을 막고, 프론트 주소만 CORS로 허용하며, 키는 서버 환경 변수에만 둡니다. 운영에서는 담당자 계정과 부서별 권한이 먼저 필요합니다. |
| 사진은 어디에 저장하나요? | 지금은 서버 디스크이고 DB에는 파일 위치만 기록합니다. 서버를 바꾸면 함께 옮겨야 해서, 다음 단계로 객체 저장소를 계획했습니다. |
| 외부 API(브이월드) 키는요? | 주소 조회는 백엔드가, 지도 타일은 프론트의 서버 함수가 키를 붙여 부릅니다. 브라우저 코드에는 키가 들어가지 않습니다. 주소 조회가 실패해도 분석은 그대로 진행합니다. |
| 테스트는 무엇을 확인하나요? | 4.4 응답 형식, 구간 확정 규칙, 검수·재분석·취소, 조치 전후 연결, 판정 소비 규칙, AI 연결, 배포 설정(HTTPS 주소·CORS) 등 59개입니다. |
| 서버가 바뀌면 무엇을 해야 하나요? | 새 서버에 백엔드와 모델을 올리고 HTTPS를 붙인 뒤, 화면의 백엔드 주소만 바꿉니다. DB는 Supabase라 그대로입니다. |
| 동시에 많이 올라오면요? | 등록은 바로 접수되고 분석만 줄을 섭니다. 대기열이 길어지면 화면에 "분석 대기 중"이 길게 보일 뿐 요청이 실패하지는 않습니다. 처리량이 필요하면 GPU 서버나 워커를 늘립니다. |
